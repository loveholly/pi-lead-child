# 诊断 bug

改编自 mattpocock/skills 的 diagnosing-bugs（MIT 许可，见同目录的 LICENSE）。按 PLC 的执行方式改过：你在后台跑，没有人实时回答你，要问的事用 request_decision，阶段结果写进 checkpoint。

难修的 bug 按下面的阶段做。跳过某个阶段时，在 checkpoint 里写明理由。

先读仓库的术语表（`GLOSSARY.md`）和要动的地方的 ADR（如果有），用它们的说法理解相关的模块。

## 打码

这个流程要你展示命令、输出和抓到的数据。展示以前，把每个密钥换成 `<REDACTED>`。反馈回路从环境变量取凭据，凭据留在环境里，不出现在你展示的内容里。抓到的请求带着认证头：只引用带信号的那几行。

打码以后的输出不够诊断时，照实说，用 request_decision 问 Lead 或用户。

## 第 1 阶段：做出反馈回路

**这是整个流程的核心。** 有一个快的、只在这个 bug 上失败的通过/失败信号，你就一定能找到原因：二分、验证假设、加探针都只是在用这个信号。没有它，读再多代码也没用。

在这一阶段多花力气。

### 做回路的办法，大致按这个顺序试

1. 在能到达这个 bug 的接口上写一个**失败的测试**：单元、集成或端到端。
2. 对正在运行的开发服务器发 **curl 或 HTTP 脚本**。
3. 用固定的输入**调用 CLI**，把输出和已知正确的快照比较。
4. 用**无头浏览器脚本**（Playwright、Puppeteer）驱动界面，断言 DOM、控制台或网络请求。
5. **重放抓到的数据**：把真实的请求、载荷或事件日志存成文件，单独送进那段代码。
6. **一次性的测试架子**：只起系统的一小部分（一个服务，依赖用假的），一次函数调用就走到 bug 的代码路径。
7. **属性测试或模糊测试**：bug 是「有时结果不对」时，跑 1000 个随机输入，找出失败的形态。
8. **二分的架子**：bug 出现在两个已知状态之间（提交、数据、版本）时，把「切到状态 X、检查」写成脚本，用 `git bisect run` 跑。
9. **对照回路**：同一个输入分别跑旧版本和新版本（或者两种配置），比较输出。
10. **要人参与的回路**：最后的办法。复现必须有人操作时，用 request_decision 写清要人做的每一步、要人贴回来的输出。你在后台跑，不能等人实时配合。

### 把回路收紧

有了回路以后，继续收紧它：

- 能不能更快？缓存准备工作，跳过不相关的初始化，缩小测试的范围。
- 信号能不能更准？断言这个 bug 的具体症状，而不是「没有崩溃」。
- 结果能不能更确定？固定时间，固定随机种子，隔离文件系统，切断网络。

30 秒一次、时好时坏的回路，比没有回路好不了多少。2 秒一次、结果确定的回路，才是收紧了的回路。

### 时有时无的 bug

目标不是干净的复现，而是**更高的复现率**。把触发动作循环 100 次，并行跑，加压，缩小时间窗口，插入等待。复现率 50% 的 bug 能诊断，1% 的不能：一直提高复现率，直到能诊断。

### 真的做不出回路时

停下，照实说，列出你试过的办法。用 request_decision 向 Lead 或用户要下面三样之一：

- 能复现的环境的访问权限；
- 打过码的现场数据（HAR 文件、日志、core dump、带时间戳的录屏）；
- 允许在生产环境临时加探针。

没有回路，整张工单就做不下去时，用 ticket_update(status='blocked') 写明卡在哪里、怎样解开。**没有回路，不要开始猜原因。**

### 完成标准：一个收紧了、能变红的回路

第 1 阶段完成时，你要能说出**一条命令**（脚本路径、测试命令或 curl）。你**已经跑过它至少一次**（贴出命令和打码以后的输出），而且它：

- **能变红**：走真实的 bug 代码路径，断言用户或工单描述的**那个症状**。bug 在时失败，修好以后通过。只是「跑得起来」不算。
- **确定**：每次跑的结论一样。时有时无的 bug，固定在一个足够高的复现率。
- **快**：几秒，不是几分钟。
- **不用人**：你自己能跑。要人参与时，只按上面第 10 条的方式。

如果你发现自己在这条命令出现以前就在读代码猜原因，**停下：直接跳到假设，正是这个流程要防的错。** 没有能变红的命令，不进第 2 阶段。

完成以后提交一个 checkpoint（kind='milestone'），summary 里写这条命令和它的结果。

## 第 2 阶段：复现，再缩小

跑回路，看它在 bug 出现时变红。

确认三件事：

- 回路复现的是**用户或工单描述的**失败，不是旁边另一个碰巧出现的失败。bug 认错了，修的也是错的。
- 失败能反复复现。时有时无的 bug，复现率要高到能诊断。
- 记下了确切的症状（报错、错误的输出、慢的时间）。后面的阶段用它核实修复真的对上了这个症状。

### 缩小

回路变红以后，把复现缩小到**仍然变红的最小场景**。一次去掉一样：输入、调用方、配置、数据、步骤。每去掉一样就重跑回路，只留下导致失败必需的部分。

最小复现让第 3 阶段要怀疑的东西更少，也是第 5 阶段干净的回归测试。

**剩下的每一样都必需**时，这一步才算完成：去掉任何一样，回路就变绿。

复现了、缩小了，才往下走。

## 第 3 阶段：提假设

先列出 **3 到 5 个排好序的假设**，再测其中任何一个。只想一个假设，会被第一个看起来合理的想法带偏。

每个假设都要**能被证伪**：写出它的预测。

> 格式：「如果原因是 X，那么改变 Y 会让 bug 消失，改变 Z 会让它更严重。」

写不出预测的假设只是感觉：去掉它，或者把它改准确。

**把排好序的清单写进一个 checkpoint**（kind='milestone'），再开始测。Lead 和用户看到清单，可能马上知道哪一条已经排除了、哪一条最可能（「我们刚改过第 3 条说的地方」）。不要等回复，按你的排序接着做。收到回复时再调整。

## 第 4 阶段：加探针

每个探针都对应第 3 阶段的某一条预测。**一次只改一个变量。**

工具按这个顺序选：

1. 环境支持时，用**调试器或 REPL** 查看。一个断点胜过十行日志。
2. 在能区分假设的边界上加**有针对性的日志**。
3. 不要「什么都打日志，再 grep」。

**每一行调试日志都加唯一的前缀**，例如 `[DEBUG-a4f2]`。最后清理时 grep 一次就够：带前缀的日志一定会被删掉，不带前缀的会漏掉。

**性能问题走另一条路。** 性能退化时，日志通常帮不上忙。先建立基线测量（计时的架子、`performance.now()`、profiler、查询计划），再二分。先测量，再修。

## 第 5 阶段：修复，补回归测试

有一个**对的接口**能测时，先写回归测试，再修。

对的接口，是测试在那里重现了这个 bug 在真实调用处的样子。如果只有太浅的接口，那里的回归测试只会给人假的信心。例如：bug 要多个调用方才出现，测试只有一个调用方；单元测试复现不了触发 bug 的那一串调用。

**没有对的接口，这本身就是一个发现。** 记下来：代码的结构让这个 bug 没法被测试锁住。把它写进交付的 outcome，交给 Lead。

有对的接口时：

1. 把最小复现变成在这个接口上失败的测试。
2. 看它失败。如果你是改了代码或测试数据才让它失败的，和原始版本 `diff` 一次，证明改动真的生效了，再相信这个失败。
3. 修复。
4. 看它通过。
5. 对原始的（没有缩小的）场景重跑第 1 阶段的回路。

## 第 6 阶段：收尾

交付（ticket_update(status='review')）以前，下面每一项都要做完：

- [ ] 原始的复现不再复现（重跑第 1 阶段的回路）。
- [ ] 回归测试通过，或者写明了为什么没有对的接口。
- [ ] 所有 `[DEBUG-...]` 探针都删掉了（grep 这个前缀）。
- [ ] 一次性的原型删掉了，或者移到了明确标为调试用的地方。
- [ ] 最后证实的那个假设写进了提交说明和 outcome 的 summary，下一个排查的人能学到。回路的命令和修复前后的结果写进 outcome.validations。
